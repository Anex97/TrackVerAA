# 4.3 Especificación de Requerimientos

## Introducción

La especificación de requerimientos es el proceso mediante el cual se identifican,
documentan y validan las necesidades y restricciones que debe satisfacer un sistema
de software. Sommerville (2016) define los requerimientos como "descripciones de
los servicios que debe proporcionar el sistema y las restricciones bajo las cuales
debe operar", y los clasifica en requerimientos funcionales, que describen lo que
el sistema debe hacer, y requerimientos no funcionales, que describen las
propiedades y restricciones del sistema.

Para TrackVer A&A, los requerimientos fueron levantados a partir de la información
proporcionada por el técnico instalador de GPS, quien actúa como informante clave
y cliente principal del proyecto, complementados con el análisis del problema
identificado en la etapa de diagnóstico.

---

## Requerimientos Funcionales

Los requerimientos funcionales, según Sommerville (2016), son declaraciones de
los servicios que el sistema debe proveer, cómo debe reaccionar ante entradas
específicas y cómo debe comportarse en situaciones particulares. A continuación
se presenta la especificación de requerimientos funcionales de TrackVer A&A:

### RF-01: Autenticación de Usuarios

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-01 |
| **Nombre** | Autenticación y control de acceso por roles |
| **Descripción** | El sistema debe permitir el inicio de sesión mediante credenciales (usuario y contraseña) y asignar automáticamente el menú y las funcionalidades correspondientes según el rol del usuario (Administrador, Auditor o Usuario). |
| **Prioridad** | Alta |
| **Entrada** | Nombre de usuario y contraseña |
| **Proceso** | Validación de credenciales contra la base de datos `usuarios.db` y asignación de rol |
| **Salida** | Redirección al menú correspondiente según el rol autenticado |
| **Restricción** | El sistema debe bloquear el acceso tras 3 intentos fallidos consecutivos |

---

### RF-02: Visualización de Posiciones en Tiempo Real

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-02 |
| **Nombre** | Visualización GPS en mapa interactivo |
| **Descripción** | El sistema debe mostrar en un mapa interactivo la última posición conocida de cada dispositivo GPS registrado, actualizable de forma periódica sin necesidad de recargar la página. |
| **Prioridad** | Alta |
| **Entrada** | Datos de posición GPS recibidos del dispositivo (latitud, longitud, timestamp) |
| **Proceso** | Consulta de la última posición almacenada en `posiciones.db` y renderizado en mapa con Leaflet.js |
| **Salida** | Marcadores en el mapa indicando la posición actual de cada unidad |
| **Restricción** | El mapa debe actualizarse en intervalos máximos de 30 segundos |

---

### RF-03: Almacenamiento de Historial de Posiciones

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-03 |
| **Nombre** | Almacenamiento y consulta de historial GPS |
| **Descripción** | El sistema debe almacenar todas las posiciones GPS recibidas con su marca de tiempo correspondiente, y permitir la consulta del historial de recorridos filtrando por unidad y rango de fechas. |
| **Prioridad** | Alta |
| **Entrada** | Datos de posición GPS (latitud, longitud, timestamp, ID de dispositivo) |
| **Proceso** | Almacenamiento en `posiciones.db` y consulta con filtros de fecha y unidad |
| **Salida** | Lista de posiciones y trayectoria dibujada en el mapa para el periodo seleccionado |
| **Restricción** | El historial debe conservarse por un mínimo de 90 días |

---

### RF-04: Gestión de Geocercas

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-04 |
| **Nombre** | Creación y administración de geocercas |
| **Descripción** | El sistema debe permitir al Auditor y al Administrador crear, editar y eliminar zonas geográficas (geocercas) sobre el mapa, asociándolas a uno o varios vehículos registrados. |
| **Prioridad** | Media |
| **Entrada** | Coordenadas del polígono o radio de la geocerca, nombre y vehículos asociados |
| **Proceso** | Almacenamiento de la definición geométrica de la geocerca y asociación con dispositivos |
| **Salida** | Geocerca visible en el mapa con identificación de nombre y estado |
| **Restricción** | Cada vehículo puede tener asociadas hasta 10 geocercas simultáneas |

---

### RF-05: Comandos Remotos

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-05 |
| **Nombre** | Envío de comandos remotos a dispositivos GPS |
| **Descripción** | El sistema debe permitir al Auditor y Administrador enviar comandos remotos a los dispositivos GPS registrados, incluyendo el apagado remoto del vehículo, con registro del comando enviado, usuario que lo ejecutó y timestamp. |
| **Prioridad** | Media |
| **Entrada** | Selección del dispositivo y comando a ejecutar |
| **Proceso** | Envío del comando al dispositivo y registro en base de datos |
| **Salida** | Confirmación de envío del comando y actualización del estado del dispositivo |
| **Restricción** | Solo usuarios con rol Auditor o Administrador pueden ejecutar comandos remotos |

---

### RF-06: Gestión de Usuarios y Dispositivos

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-06 |
| **Nombre** | Administración de usuarios y dispositivos |
| **Descripción** | El sistema debe permitir al Administrador crear, editar, desactivar y eliminar cuentas de usuario, así como registrar, configurar y dar de baja dispositivos GPS en el sistema. |
| **Prioridad** | Alta |
| **Entrada** | Datos del usuario (nombre, correo, rol, contraseña) o datos del dispositivo (ID, modelo, vehículo asociado) |
| **Proceso** | Operaciones CRUD sobre `usuarios.db` y tabla de dispositivos |
| **Salida** | Confirmación de la operación y actualización de la lista correspondiente |
| **Restricción** | Solo el Administrador puede realizar operaciones de gestión de usuarios y dispositivos |

---

### RF-07: Alertas por Geocerca

| Campo | Descripción |
|-------|-------------|
| **ID** | RF-07 |
| **Nombre** | Generación de alertas por violación de geocerca |
| **Descripción** | El sistema debe generar y registrar una alerta automática cuando un vehículo entre o salga de una geocerca configurada, notificando al usuario responsable desde la interfaz del sistema. |
| **Prioridad** | Media |
| **Entrada** | Posición GPS del vehículo y definición de geocercas activas |
| **Proceso** | Comparación de posición actual contra límites de geocercas activas |
| **Salida** | Alerta visible en el panel del usuario con detalle de unidad, geocerca y timestamp |
| **Restricción** | Las alertas deben registrarse aunque el usuario no esté conectado al sistema en ese momento |

## Requerimientos No Funcionales

Los requerimientos no funcionales, de acuerdo con Sommerville (2016), son
restricciones sobre los servicios o funciones ofrecidas por el sistema, e incluyen
restricciones de tiempo, restricciones sobre el proceso de desarrollo y restricciones
impuestas por estándares. Estos requerimientos frecuentemente son más críticos
que los funcionales, ya que un fallo en su cumplimiento puede hacer que el sistema
completo sea inaceptable.

### RNF-01: Usabilidad

| Campo | Descripción |
|-------|-------------|
| **ID** | RNF-01 |
| **Categoría** | Usabilidad |
| **Descripción** | La interfaz de usuario debe ser responsiva, intuitiva y accesible desde navegadores web modernos (Chrome, Firefox, Edge) sin necesidad de instalación de software adicional por parte del usuario final. |
| **Criterio de aceptación** | Un usuario sin entrenamiento previo debe ser capaz de consultar la posición de un vehículo en el mapa en menos de 2 minutos desde el inicio de sesión. |

---

### RNF-02: Rendimiento

| Campo | Descripción |
|-------|-------------|
| **ID** | RNF-02 |
| **Categoría** | Rendimiento |
| **Descripción** | El sistema debe responder a las solicitudes de visualización del mapa y consulta de historial en un tiempo máximo de 3 segundos bajo condiciones normales de red y con hasta 500 dispositivos registrados. |
| **Criterio de aceptación** | Medición de tiempos de respuesta en pruebas de carga con 500 registros en base de datos. |

---

### RNF-03: Seguridad

| Campo | Descripción |
|-------|-------------|
| **ID** | RNF-03 |
| **Categoría** | Seguridad |
| **Descripción** | El acceso a los datos y funcionalidades debe estar restringido según el rol del usuario autenticado. Las contraseñas deben almacenarse de forma cifrada y no en texto plano. |
| **Criterio de aceptación** | Ningún usuario puede acceder a rutas o datos de un rol superior al suyo. Las contraseñas en base de datos no son legibles en texto plano. |

---

### RNF-04: Portabilidad

| Campo | Descripción |
|-------|-------------|
| **ID** | RNF-04 |
| **Categoría** | Portabilidad |
| **Descripción** | El sistema debe poder ejecutarse en cualquier entorno con Java 17 instalado, sin dependencia de sistemas operativos específicos, y utilizando SQLite como motor de base de datos para evitar la necesidad de servidores de base de datos externos. |
| **Criterio de aceptación** | El sistema se ejecuta correctamente en Windows 10/11 y en distribuciones Linux comunes sin modificaciones de código. |

---

### RNF-05: Mantenibilidad

| Campo | Descripción |
|-------|-------------|
| **ID** | RNF-05 |
| **Categoría** | Mantenibilidad |
| **Descripción** | El código fuente debe estar documentado con comentarios descriptivos, organizado en paquetes por responsabilidad (modelo, vista, acceso a datos) y versionado en un repositorio Git con mensajes de commit descriptivos. |
| **Criterio de aceptación** | Un desarrollador externo puede comprender la estructura del proyecto y realizar una modificación menor en menos de 2 horas de revisión del código. |
